# Observing public development without inventing a verdict

The owner console reads only the bound public account's intellectual operation
lifecycle: reserved, received, accepted, rejected, unavailable and no-change.
It distinguishes a stored proposal from a null proposal and reports recorded and
redacted revision counts. These are journal facts. They do not establish that a
position is currently eligible, independently verified, useful or developing well.
In particular, many no-change results are not an instruction to manufacture views.

Operation references are opaque digests. The read interface returns no proposal
text, state fields, dependency ancestry, participant identities, private operations
or model metadata. Owner authentication does not authorize private participant
history. Current positions require the full live source/consent/mission validation
used by the intellectual context adapters; a revision count cannot replace it.

Reply and mention polling are shown separately. Each has its latest attempt,
recorded statuses and received/pending input counts. No attempt differs from a
failed attempt and from a committed empty page. Historical totals are not process
health, freshness or permission to call a provider. The interface does not say
that the absence of locally observed comments proves that Threads has none.

Research observation separates completed reports, uncertain operations, started
work, held work, failed work and the recorded allowance-exhausted subset of
failures. It does not expose questions, report prose or raw errors. A report is
evidence available for consideration, not proof of a changed belief or semantic
support. Local operation counts are not provider billing.

This is a read-only application change. It adds no polling call, inference,
permission, grant, wallet reset or owner command. Offline tests cover scoped
stores, missing/failed polling, denial categories and the actual browser display.
Real behavioral acceptance remains separate.

## Monthly wallets

The existing peer-authenticated diagnostics response can optionally include a
bounded wallet observation. Configure the worker-owned telemetry process with
`--monthly-budget /absolute/worker-owned/wallet.sqlite`. Missing configuration
or unreadable state appears as unavailable, never a zero balance or new budget.
Old workers retain their exact diagnostics response; the owner accepts either
shape. This setting reads an existing pinned protected file and never creates a
wallet, updates its clock watermark, clears holds or changes its policy.

The owner sees the UTC month, lane, limit, settled local accounting, all unresolved
reservations (including earlier months), remaining conservative allowance and
whether that wallet can admit the next fixed reservation. Research also shows
attempts in the current month against the existing 100-search bound. This is not
provider billing, total organization credit, a running-process verdict, or new
authorization. Stop, account/grant authority and other worker checks still apply.
The public $15 Sol / $5 research partition and separate $10 private wallet remain
unchanged. Existing authenticated Stop controls stop new work; this read-only
extension adds no budget editor, spend-suspension reset or worker resume command.

No project identifier, path, operation identity, token, question or transcript
crosses this observation boundary. Freshness and a closed typed shape are checked
by the owner client. Offline tests exercise real SQLite and local authenticated
sockets, old-month unknown holds, independent search-count exhaustion, file
replacement, missing/corrupt state and the real owner browser display.
