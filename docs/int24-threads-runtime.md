# INT-24 public Threads runtime

INT-24 adds an explicitly configured, default-disabled public coordinator. It is an offline integration implementation, not evidence that a live Threads account, OpenAI project, disclosure, or operator procedure is ready. No real credential, Meta/OpenAI request, profile change, publication, or deployment was used to develop or test it.

## Boundary and lifecycle

- `ThreadsStage0` retains its exact `RecordedBehaviorModel` and `ThreadsSimulator` restrictions. The new `ThreadsRuntime` is constructed separately and accepts exact `PublicBehaviorClient` and `ThreadsHTTPTransport` components with a Stage 3 account policy. The durable Stage 0 journal and scheduler handoff methods are reused without changing Stage 0 guards. The public coordinator requires its own versioned journal marker and intent version; an existing Stage 0 journal or synthetic approval record cannot authorize it. The runtime stays disabled unless both `enabled` and `live_enabled` are set. The operator command requires `--activate-live` and a private, reviewed configuration file.
- A scheduled wakeup or a verified, stored reply/mention produces an application-owned operation ID. The journal commits `started` before the worker exchange. A crash, timeout, malformed response, or lost worker reply leaves this operation uncertain; neither restart nor a duplicate poll replays inference. The worker authenticates the application UID, checks the exact started operation and digest of its public context against the journal, and reserves a one-use attempt in its own database before calling the SDK. The client authenticates the worker UID. The worker owns model selection, SDK credential, zero-retry configuration, no-tool request, no provider storage, output budget, and timeout. The public request has a separate closed schema; it does not reuse the private conversation model contract. The journal keeps a digest of the public event text for this check and uses UTF-8 JSON so a bounded newly generated Russian draft fits its existing payload limit. Oversized verified events are durably rejected before model contact without stopping independent event processing.
- Model context contains Core Self, one verified public event if present, and a verified mission text if configured. Public text, mission text, and model output are data. They cannot choose the account, parent, approval, scopes, source provenance, or route. `reply` is accepted only for a verified inbound event and `propose_publication` only for a wakeup. `no_action` is valid and durable. All other decisions are explicitly rejected in this runtime. A Russian output gate and Threads content bound apply to new drafts. The runtime does not accept private-derived publication.
- An accepted publication is handed to the existing immutable Threads outbox as public provenance and waits for independent approval. The local operator procedure authenticates the configured OS UID and records the actor, purpose, expiry, exact outbox binding, and revocation in the durable journal. The authorization provider rechecks that binding, source, mission, privacy-control generation, approval validity, stop, spend, route and account before effect. Changing a draft or source cannot reuse approval. The inherited Threads service reserves and audits effects, verifies the account before writes, pauses the account on `UNKNOWN`, and reconciles only a recorded exact publication ID. It never searches by text or resends an uncertain write.
- Stage 3 G controls include account, scope, route, content, lifecycle and bounded HTTP checks. The Russian H gate is heuristic. M concerns such as harmful claims, harassment, privacy inference and narrative truth require separate human review; this code does not claim semantic guarantees. There is no publication quota or activity target. The Core Self and disclosure policy still require honest AI identification, and fictional autobiography cannot be represented as operational memory or evidence.

## Local commands and protected configuration

Run `python -m ops.int24_threads_runtime readiness` to see the disabled state without reading a token or making a network request. All other commands require `--activate-live --config /protected/operator.json`. Supported commands are `wakeup ID`, `poll reply|mention`, `process reply|mention`, `draft OPERATION`, `approve OPERATION`, `revoke APPROVAL`, `dispatch OPERATION`, `reconcile OPERATION`, `recover-sending OPERATION`, `approve-reconciliation-recovery OPERATION`, and `recover-reconciliation OPERATION APPROVAL`. The approval responses include exact revocable references. A single poll is capped at one page, ten events and ten seconds; processing is capped at ten events. The worker command is `python -m ops.int24_public_worker --config /protected/worker.json`. These entrypoints are manual, not services or scheduled jobs.

The operator configuration, Threads token file, worker configuration, and OpenAI key file must each be an owner-only `0400` regular file in a `0700` directory as required by the protected-file loader; the operator configuration supplies `activation_reviewed: true`, account and exact Meta user/root IDs, actual reviewed scope names, protected Threads token file, paths for the worker socket, journal, scheduler, outbox, owner directory, event store and ledger, worker UID, and operator UID/actor. It may supply `public_mission_path`: a protected `0600` JSON file with exactly `version`, `purpose`, `text`, `activated_at`, and `parent_version`. The text must match the existing closed purpose catalog and activation time must have arrived. The coordinator binds the exact version, purpose and digest at inference, handoff, approval and dispatch; a changed mission invalidates the draft. The `discontinue_optional_channel` purpose denies publication. The worker's protected `0400` configuration supplies `worker_enabled: true`, the reviewed OpenAI `project_id` and `organization_id`, model, separate OpenAI key file, journal and attempt paths, `event_store_path`, socket path, application UID and the socket group. Both billing IDs are validated and passed explicitly to the SDK. The worker must have write access to the same event store used by the application so inference attempts, usage and confirmed spend suspension are durable and visible to its stop gate. Its attempts database has a versioned schema and an operation primary key; a stale table without that constraint is rejected. Run the worker under a separate restricted UID. Provision its socket directory and group so only the application UID can connect; allow the worker read-only access to the public journal while keeping its credential and attempt database inaccessible to the application UID. The worker socket uses mode `0660` when a group is configured. The local operator account must be a dedicated administrative UID; ordinary participant sessions and public messages never call this procedure. Protect all configured paths and backups by the deployment's access policy.

The flags and scope strings are only configuration claims. Before any activation, the human operator must separately review:

1. The public profile and entry disclosure in Russian: truthful AI identity, fictional narrative status, processing and privacy limitations, and the intended public account. Do not change the profile as part of this PR.
2. The exact Meta app, account ID, root post ID, granted scopes, App Review status, token validity and refresh/revocation plan. Validate `GET /me`, reply/mention fields, two-step publishing and readback under a separately authorized live smoke. A configured scope name is not granted permission evidence.
3. The OpenAI project/model, paid-call budget and hard spend limit, credential ownership and rotation, restricted worker UID, journal access, socket permissions, SDK zero-retry behavior, incident stop and recovery procedure.
4. The local owner stop state, privacy controls, mission snapshot, publication policy, Russian H gate, human M review, rate limits, retention/audit access, and a reviewed dry run with no real publication.
5. An explicit authorization for each proposed draft. Approval expiry is bounded to 1–60 minutes in the operator command. Dispatch is a separate command. After a crash leaves `SENDING`, run `recover-sending`; it returns to `READY` only with durable proof that no publication effect started, otherwise it moves to `UNKNOWN`. If a reconciliation claim was interrupted, issue a purpose-bound `approve-reconciliation-recovery`, then use its reference with `recover-reconciliation` to clear only that claim before retrying reconciliation. On `UNKNOWN`, keep the account paused and inspect exact provider evidence; do not reset, restart, abandon or replace the draft to resend it.
