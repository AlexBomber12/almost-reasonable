# B07A: participant-private narrative continuity

Narrative memory is optional and off by default. Select it in the private application with `--enable-narrative --narrative-permission /protected/control/narrative.json --narrative-pilot-id PILOT_ID`. The credential-owning worker separately needs `--narrative-permission /protected/control/narrative.json`. Both processes must read the current protected permission before their respective operations. The file has the closed form:

```json
{"version":"private-narrative-permission-v1","pilot_id":"synthetic-pilot-id","max_operations":1}
```

The pilot ID must match the worker's current activation. The v1 application and worker accept a limit of exactly one additional operation per pilot. For the explicitly scoped [B03E combined acceptance](b03e-combined-acceptance.md), `private-narrative-permission-v2` requires exactly 20 operations, equal to the B03E activation total; its `max_operations` counts **all additional memory/evolution/typed/shared/narrative operations together**, not just narrative operations. The application verifies the v2 format and pilot ID; the worker additionally enforces the live activation cap and durable shared additional-operation count. The worker checks live permission for episode proposals and for normal replies carrying narrative context, including first turns with no stored episode; a normal reply uses its base allowance rather than an additional narrative allowance. A narrative proposal is admitted only when two global allowance slots remain; its reply slot is held in the same transaction and claimed once by the matching `reply:` operation. A failed or interrupted turn conservatively keeps that slot consumed. The application checks its configured pilot ID, file safety, Stop, spend, current session and privacy authority. A missing, changed or invalid permission blocks new narrative work and release. This switch does not create an activation, make a paid call, enable public sharing or deploy a service. Narrative continuity may run with generic extraction or evolution and typed memory in the same private conversation. Shared proposals remain incompatible with narrative mode. Bounded public research may share this runtime through the existing reviewed catalog and authenticated chat path; see [B05E operation and limits](b05d-research-deployment.md#b05e-memory-narrative-and-research-in-one-conversation). The default worker runtime and its existing provider-operation count remain unchanged.

[Ordinary operating grants](private-operating-grant.md) add narrative permission
`private-narrative-permission-v3` with an operator-selected positive shared
additional-operation cap, bounded by the ordinary grant, without acceptance flags
or synthetic task IDs. Legacy v1/v2 limits above remain unchanged.

For a combined runtime, the finite order is generic evolution (or extraction when evolution is disabled), typed memory, an explicitly cued narrative proposal, then the reply. Each enabled ordinary memory family costs at most one provider operation per turn. Evolution suppresses redundant extraction. An ordinary turn therefore uses at most three operations with both memory families enabled; an explicit fictional-story turn uses at most four. The narrative proposal and matching reply retain the existing atomic two-slot allowance reservation. Every operation has a stable identity derived from the initiating event, and an interrupted or uncertain operation is never retried against changed context.

Only turns that explicitly request a fictional story or narrative continuation request a narrative proposal; factual uses such as “user story,” “news story,” and “narrative medicine” stay on the ordinary reply path. The ambiguous Russian word `история` triggers this extra operation only in a standalone story request such as `Расскажи историю` or `Продолжим историю`; a factual history question such as `Расскажи историю Рима` does not. Explicit non-fiction or negated fiction requests also stay on the ordinary reply path; a later, separate affirmative story clause requests narrative continuity. Ordinary turns can still read eligible episodes for continuity without spending an additional narrative operation. Each admitted narrative turn has one stable `narrative:` operation identity derived from its original input event. The worker may return one `create`, one `revise` of a shown opaque handle, or `no_change`. At 16 current episodes, creation is forbidden in the worker request and rejected by the application; revision-16 episodes remain available to replies but have no revisable proposal handle. A cued reply reserves one of its 16 dependency slots for its own accepted episode. No loop or automatic retry follows a lost response. A separate application IPC attempt and worker allowance entry account for the operation. The source-bound application receipt persists the visible head snapshot, selected handle mapping, full reply source set and received proposal. A successful proposal is projected into the same-turn reply as typed untrusted fiction. The episode is saved only after a reply draft persists, and the reply receives a protected dependency edge before release. A failed reply leaves no new episode. A research decision is an alternative to the ordinary reply: its durable intent rejects and erases the received narrative proposal, and recovery recognizes that intent before considering any episode commit. A research report never acknowledges an episode. The inference operation has already claimed its held reply slot once; research separately consumes its existing catalog quota and provider accounting, with no refund or extra inference call. An episode committed before its creating reply is released stays out of later model context until that reply is released. A crash after a received proposal can reconcile it; an exact already-committed episode is recognized without repeating the write. If the process exits before reply inference begins, the held reply is resolved as unavailable rather than retried with a changed context. An abandoned reserved receipt also resolves unavailable, while an active same-process turn is left running. A reserved or uncertain provider outcome is never resent. An old receipt cannot target a new current head. Stop, spend, session, permission and privacy checks occur before admission, receipt, commit and release.

EventStore v12 stores fictional `narrative_items`, immutable `narrative_operations`, removable `narrative_payloads`, protected source and context edges, and reply-to-episode edges. An episode is limited to 4 KiB. The store permits at most 16 current episodes per participant and 16 revisions per item. Each revision binds at most 100 complete source events and at most 16 exposed episode operations. The trusted application chooses item and operation IDs, principal, timestamp, expected revision and all dependencies. Compare-and-swap checks every current head and source in the same write transaction. Model text and handles cannot grant consent, verification, audience, or source authority. The tables never enter factual state, generic memory, event history or research evidence. Repeated fiction remains fiction.

The private context projection ranks complete, currently eligible participant-scoped ordinary memories and fictional episodes, and admits only whole records while the combined request and 100-source reply bounds fit. Ordinary memories retain their kind, provenance, verification and untrusted-memory labels. Episodes retain fixed `fictional_autobiography`, `untrusted_fiction_data`, `can_instruct=false`, `verified_action=false` and `evidence=false` labels. Protected IDs stay in receipt and reply edges, outside provider requests. Generic and typed writers see only the initiating participant input and their own factual memory heads; fictional episode text never enters their proposal requests. The narrative proposal worker receives whole selected prior conversational segments and episode text as untrusted data; its complete material source union comes from the reserved reply. A subsequent conversation and process restart read the same current episode heads. Old revisions remain distinct and inspectable in storage rather than silently overwriting history.

General AI and fiction disclosure remains in the profile and private chat entry. First-person fictional memories need no label on every story. A direct question about whether an event really happened requires an accurate distinction between fiction and actual activity. The provider instruction makes this distinction explicit, but fake-provider tests establish only contract shape and deterministic data flow. Real-model semantic reliability, including consistency and direct-question truthfulness, remains unproven.

Deleting a private source removes every dependent episode payload and invalidates its operation and reply edges. Revision and conversation context carry the full inherited source union, so a derived episode or historical reply remains withheld after transitive deletion. Reconciliation replays current deletion and revocation state against an older backup before reads are eligible. Independent participant records remain. Fiction disclosure does not authorize sharing; this feature creates no public projection or sharing path.

`tests/test_narrative.py` uses fake provider responses, AF_UNIX worker IPC and real local SQLite stores for create, revision, no-change, restart continuity, A/B isolation, injection and forged authority metadata, stale state, receipt recovery, permission changes, deletion, old-backup quarantine and independent record preservation. The complete repository gate is `scripts/ci.sh`; process and socket tests also require current-HEAD GitHub Actions. Remaining B07 work includes human evaluation of natural narrative consistency and truthful reality answers, live semantic checks, operational activation review and full MVP acceptance. This package supplies participant-private continuity only; it does not create a global public biography.
