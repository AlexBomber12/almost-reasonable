# Protected public-to-private intellectual influence

This completes the public-to-private source path alongside the bounded rhythm and
owner controls in `agent-rhythm-owner-controls.md`. Real-model behavioral acceptance,
two actual participants and provider/Meta production validation remain separate.

## Activation and boundaries

The private worker entrypoint accepts `--public-intellectual-config PATH` only in
worker mode. The protected owner-owned file is a regular mode 0400 file in a mode
0700 directory. Its closed shape is `version: public-intellectual-source-v1`,
`account`, absolute `journal_path`, `threads_path`, `ledger_path`, `mission_path`
(null when absent), and `owner_directory`. The configured owner directory must
match the private console/application and the public runtime's actual recorded
binding. No configuration means no new public intellectual sources are admitted.

For public states with private shared ancestors, configure the existing shared
intelligence against the same private EventStore and privacy ledger. The receiving
runtime rejects a foreign private store or ledger. The adapter rechecks both the
public account's allowed source and the receiving participant's allowed shared
audience. A public-only audience does not authorize private B retrieval.

The adapter reads existing public journal, Threads and control stores read-only;
it never initializes a missing database. It reads no provider credential and
makes no HTTP or model request. Only bounded agent-owned state descriptions enter
the actual private SDK input, as unverified data. Private source identities,
account identifiers, paths, bindings and routing receipts stay in the application.
Importing intellectual development grants no tools, spending, scheduling or public
publication authority and does not merge private A/B histories.

New-context selection remains capped at six eligible public records. Revalidation
resolves the exact required current keys independently of selection order, within
the existing 100-dependency bound. A still-valid older source does not disappear
from dependent private replies, state or fiction when six newer heads arrive.
Historical validation records do not become additional new-context source handles.
Each converted record must fit the source projection's existing byte limit; an
oversized conversion is skipped individually, preserving unrelated eligible
records. Revision, withdrawal, audience and control checks still apply at every
revalidation; historical receipts never grant continued authority.

The six visible source handles are separate from historical receipts. Graph and
quarantine validation permit the exact inherited receipt set up to the existing
100-dependency limit and enforce the same 45,056-byte protected
dependencies/receipts budget as admission. Each receipt still requires its closed
shape, exact key/binding, routed shared ancestors, event roots and any displayed
record binding. Multi-turn histories can accumulate more than six receipts while
remaining reconcilable, erasable and restorable; legacy snapshots without external
receipts retain their validation behavior.

## Protected ancestry and recovery

Every imported state has a closed `public-intellectual-receipt-v1` receipt binding
account/item/revision, state and dependency digests, the exact displayed record,
public control generation and all private shared ancestors. Its source key is
opaque. The optional `external_receipts` map lives in the existing protected
intellectual operation snapshot, within its size and dependency bounds. Legacy
snapshots remain valid. Receipts are historical routing evidence, never proof of
current source availability or independent factual verification.

Admission carries every imported shared ancestor into the actual reply's
`protected_reply_shared` graph. Existing context binding flattens those ancestors'
private source events into the intellectual snapshot. Quarantine joins the closed
receipt to that exact routed reply, its shared ancestors, their event roots and
the displayed projection. Missing, foreign, malformed or mismatched receipts fail
closed. Merely presenting a well-shaped public hash cannot replace these edges.

The existing deletion graph now reaches imported private replies, intellectual
revisions and downstream context. Reconciliation of an old backup applies the
latest private deletion ledger to the restored graph and physically removes those
derived payloads while retaining unrelated participant input. External source
availability is rechecked before inference, persistence and release. A restored
receipt cannot grant continued use: absent configuration or a withdrawn public
source hides dependent history, heads and fiction from subsequent retrieval.

Shared source selection inside a private request uses its already-held privacy
fence and connection. It does not acquire a second writer fence on the same
ledger. Independent public callers retain the original gated source read.

Optional public influence is selected only when its complete shared ancestry,
including every protected event root, fits the reply's dependency and byte limits.
An overfull optional record is omitted before inference; it cannot turn an
otherwise valid private message into a failed reply reservation.
Each public record must also fit the private receipt's 16-shared-ancestor bound.
An unimportable record is skipped individually, preserving other eligible public
heads in ordinary selection and exact-key historical validation.

## Validation scope

Offline regressions exercise actual local worker IPC and SDK input, separate A/B
histories, public-only audiences, source withdrawal before/during provider work,
derived narrative, protected graph reconstruction, corrupted backup rejection and
physical erasure after old-backup restore. SDK/provider HTTP are fakes. Those
tests establish implementation behavior; they do not supply real-model M1–M6 or
SCN-01–12 acceptance, real participant evidence, or production readiness.

The private intellectual prompt version is `agent-intellectual-state-prompt-v4`. The state
projection remains version 1. Old implementations reject the new receipt/source
shape; review coordinated application/worker compatibility before any separately
authorized deployment. This change activates no live process or grant.
