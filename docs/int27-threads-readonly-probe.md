# INT-27 Threads read contract probe

This operator tool is disabled by default. `python -m app.ops.int27_threads_readonly_probe` prints `{"state":"disabled","requests":0}` without reading a configuration, token, owner store, or network. The separate `run` command is reserved for a later, explicitly authorized operator verification. This task did **not** run it against Meta.

## Official read contracts checked on 2026-10-26 (B11A)

Meta's developer documentation settles the route question: the [User reference](https://developers.facebook.com/documentation/threads/reference/user#get-threads-user-idmentions) explicitly defines `GET /{threads-user-id}/mentions`, and the [Mentions guide](https://developers.facebook.com/documentation/threads/threads-mentions) uses that route. Retain the configured ID route. The supplementary [official Postman example](https://www.postman.com/meta/threads/request/34203612-fc3f21da-0a53-44ab-80e2-8cd8c376a42a) uses `/me/mentions`; this task neither substitutes that alias nor assumes the routes are interchangeable.

| Read | Supported request and evidence | Required permissions |
| --- | --- | --- |
| Account | `GET /v1.0/me?fields=id`; [Profiles](https://developers.facebook.com/documentation/threads/threads-profiles) documents the app-scoped profile and `/me` example. Require its string ID to equal `provider_user_id` before the probe reads either stream. | `threads_basic` |
| Replies | `GET /v1.0/{reply_thread_id}/replies?fields=id,text,media_type,timestamp,root_post,replied_to,is_reply_owned_by_me&limit=10&reverse=false`; [Replies and Conversations](https://developers.facebook.com/documentation/threads/retrieve-and-manage-replies/replies-and-conversations) documents these fields, chronological order, and object relationships shaped as `{"id":"..."}`. This route returns immediate replies, so both root and parent must equal the configured top-level root, even for an owned reply that will be filtered. | `threads_basic`, `threads_read_replies` ([permissions](https://developers.facebook.com/documentation/threads/retrieve-and-manage-replies)) |
| Mentions | `GET /v1.0/{provider_user_id}/mentions?fields=id,text,media_type,timestamp&limit=10`; the [User reference](https://developers.facebook.com/documentation/threads/reference/user) documents the route, `limit` (default 25, maximum 100), and `after`. The guide links to [post fields](https://developers.facebook.com/documentation/threads/retrieve-and-discover-posts/retrieve-posts#fields). Request only those documented fields, excluding reply relationships and ownership. | `threads_basic`, `threads_manage_mentions` |

All destinations remain `https://graph.threads.net`. The [changelog](https://developers.facebook.com/documentation/threads/changelog) entry for June 7, 2024 specifies `v1.0` on that domain; June 6, 2025 and the current [overview](https://developers.facebook.com/documentation/threads/overview) support the existing domain alongside `graph.threads.com`. No new domain is needed. The retrieved changelog's latest entry is August 18, 2026; the February 13, 2026 reply-approvals addition does not make `/replies` a pending-replies read. The probe does not read pending or nested replies.

The [pagination guide](https://developers.facebook.com/documentation/threads/retrieve-and-discover-posts#pagination) explicitly says post/mention pages omit next/previous links. Reply examples also show cursor-only paging, and the [reply reference](https://developers.facebook.com/documentation/threads/reference/reply-management) accepts `after`. The transport now preserves and returns `paging.cursors.after` independently of a next link; a page without an `after` cursor ends this scan. A present malformed cursor fails the page. Links are never followed. Existing bounds, loop detection and atomic page commits remain. Mention scans restart at the head only after a completed scan; interrupted scans resume their saved cursor. Reply scans retain their last requested checkpoint after exhaustion. The probe still reads only the first page of each selected stream and never follows cursors.

No cursor migration is required: the source/account/root/stream digest and opaque cursor encoding are unchanged. Existing saved cursors are accepted and sent intact; the correction prevents premature scan completion when a response has only cursors. It cannot retrospectively recover events an older implementation failed to fetch; mention head scans can revisit older records, but a receipt does not prove historical completeness. Cursor lifetime, ordering under concurrent arrivals, and sustained-backlog completeness still need real-account observation.

Mention reply-relationship fields are not in the linked post field contract, so they are no longer requested. Nested mention relationship discovery remains unavailable; this probe establishes only the documented mention-media read. The parser retains strict validation of any unsolicited relationship objects rather than trusting malformed evidence. Without relationships, a mention retains its own provider ID as its conversation ID. Missing text on a supported image/video/carousel is filtered only after routing validation; unfamiliar shapes fail the whole page, without cursor advancement.

The transport also uses `GET /{publication_id}?fields=id,owner,replied_to` for publication verification/reconciliation. The [Media Retrieval reference](https://developers.facebook.com/documentation/threads/reference/media-retrieval) lists those fields and `threads_basic` applies. However, the post guide limits `owner` to owned top-level posts; this evidence does not settle owner readback for published replies. That separate publication prerequisite remains unresolved. B11A changes no write or reconciliation behavior and the probe never exercises them.

Documentation access limitations: the web reader returned fetch errors/HTTP 429 for developer pages. Direct unauthenticated HTTPS retrieval of their official text responses succeeded, including the guides, references and changelog above; Context7's official-document index corroborated the route, domain/version and cursor guidance. No authenticated Meta API request was made. Meta's [Postman collection](https://www.postman.com/meta/threads/documentation/dht3nzz/threads-api) is supplementary and warns its examples may lag the developer documentation. The retrieved endpoint examples put access tokens in query parameters; the existing transport keeps them in the Bearer header. Acceptance of that credential presentation by the real account remains part of the operator observation, not something a fake response establishes. Do not move the token into URLs to bypass a failed check.

## Offline evidence versus the live prerequisite

Synthetic transport/probe tests check the production URL and field sets, cursor-only pagination, durable cursor compatibility, rejection of wrong account/root/parent evidence, request/response bounds, Stop and sanitized failures. They establish code behavior, not permission grants. No production token is read in development. A real check still needs the existing unexpired Threads **user** token for the reviewed app-scoped account and the selected read permissions. An app token, handle or Instagram ID is not a substitute.

For mentions without advanced `threads_manage_mentions` access, Meta documents visibility only for mentions made by an app's Threads testers; private authors' posts are excluded. Use an already existing public tester mention if that is the app's access level. An empty page can be a valid contract observation but cannot prove expected inbound content is visible, or establish advanced access. Likewise, a replies receipt covers only immediate visible replies to the supplied owned root, not complete nested, pending, moderation or historical coverage. Known controlled content and the app's actual grants/access level must be checked by the operator independently; the probe intentionally prints no inbound IDs or text.

## Later operator procedure; requires separate authorization

1. Confirm that the probe is executed from its reviewed repository checkout with a clean index and working tree, including no untracked files. Use the ordinary AI-Server checkout and its existing Python environment; do not activate a service or change server configuration. Confirm the exact reviewed repository revision, local account reference, **app-scoped Threads user ID**, and an existing **owned top-level post ID** for `reply_thread_id` (provider ID, not a URL). All three identifiers are required by the existing configuration, even with only `mention` selected. Select `["reply", "mention"]` for both reads, or one stream for a narrower check. Confirm the existing owner Stop directory and the selected read permissions above; publishing and reply-management permissions are not required. Confirm the owner Stop is inactive. Do not clear Stop for the probe.
2. Outside the repository, prepare a private directory owned by the invoking user, mode `0700`, under a trusted directory chain. Use the existing protected Threads token file: it must be a single-link regular file owned by that user, mode `0400`, in such a directory. Do not print or inspect its contents, generate a replacement token, or copy credentials into the checkout. Do not put a token in a shell argument, environment variable, repository, or receipt. The tool does not create an authorization file.
3. Create a separate, manually reviewed single-link regular JSON configuration file in a private directory, mode `0400`, with exactly these fields. `expires_at` must be an aware ISO 8601 time in the future and no more than one hour away. Set `revision` to the exact local `git rev-parse HEAD` value. Select one or both streams in request order, with no duplicates. The example values are placeholders, not a usable authorization:

4. From that clean ordinary checkout, the inert check is `python -m app.ops.int27_threads_readonly_probe`. Only after explicit authorization for the real check, run exactly:

   ```sh
   python -m app.ops.int27_threads_readonly_probe run --config /absolute/protected/config.json
   ```

   This is one invocation for all selected streams; there is no per-operation approval. The command resolves Git relative to its own module and rejects a dirty or unrelated checkout before reading the configuration or token. Save the sanitized JSON receipt in an operator-approved location. A nonzero exit means the observation failed and requires investigation. Never rerun automatically.

The tool uses the existing `ThreadsHTTPTransport` and `HTTPSClient` with TLS verification and redirects disabled. A second boundary allows only the transport's exact `GET` URLs. It checks the existing owner Stop and configuration expiry before each request, stops after account verification on mismatch, and makes at most three requests: one account, at most one replies page, and at most one mentions page. Each page requests at most ten records: at most twenty records across both streams, or ten with one selected stream. A single-stream run makes at most two requests. Each HTTP read is bounded by the existing 2,097,152-byte response cap. The invocation has a 30-second monotonic deadline, no retry, and no pagination loop. Response links and cursors are never followed. The probe does not construct the public coordinator, model client, scheduler, publication service, outbox, or polling stores.

The receipt contains the repository revision, reviewed account and route binding, start and finish timestamps, request count, classified outcome, observed field names, and page record counts. It omits token material, headers, response bodies, and inbound text. `observed` with exit 0 means only that all selected bounded requests passed account binding and transport parsing. Require all selected operations in the receipt, and inspect their row counts and field names; zero rows do not demonstrate nonempty record fields. Entries in `observed` on a failed receipt are preliminary shapes, not successful parser validation. The receipt contains no inbound IDs or text, so it cannot attest that a particular known reply/mention was returned. `account_mismatch`, `authentication_failure`, `rate_limited`, `contract_malformed`, `response_oversized`, `deadline_exceeded`, `configuration_expired`, `owner_stop`, and other classified failures stop subsequent reads. A successful receipt does not establish App Review approval, all configured scopes, publishing permission, semantic correctness, or complete Stage 3 readiness or readiness for autonomous posting. Those remain explicit unresolved receipt entries.
